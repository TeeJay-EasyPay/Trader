# AI Trader — Independent Architecture, Production-Readiness and World-Class Review

**Reviewer:** Claude (independent, read-only forensic review — no code was modified to produce this report)
**Review date:** 2026-07-27
**Basis:** Direct reading of `src/ai_trader/` (39 files), `mobile/App.js`, `tests/` (19 files), `render.yaml`, `governance/` and `architecture/` documentation (treated as unverified claims), and `architecture/CURRENT_OPERATIONS_RECOVERY_REPORT_2026-07-27.md` (the only source of hosted-production evidence available; no raw Render logs were available locally).
**Method:** Six independent, parallel forensic passes covering (1) data/persistence architecture, (2) execution governance and canonical trade lifecycle, (3) learning architecture and worker/job/timeout root cause, (4) API and mobile truthfulness, (5) security and failure/recovery, (6) test suite and production evidence validation. Every claim below is grounded in a specific `file:line` citation from the codebase. Where evidence was unavailable, findings are marked `NOT PROVEN`. Where a mechanism exists in code but isn't demonstrably wired end-to-end into the live system, findings are marked `IMPLEMENTED BUT NOT END-TO-END PROVEN`. Where hosted production evidence directly confirms a claim, it is marked `HOSTED PRODUCTION PROVEN`.

## Executive Conclusion

AI Trader is **not currently trading autonomously in any proven sense**, and the reason is no longer mysterious: this review found and documents the specific, concrete mechanisms responsible. The system is architecturally more sophisticated and, in several areas, more carefully engineered than its recent history of repeated "stuck again" cycles would suggest — the entry-order governance chain, the Kraken personal-holdings exclusion logic, and the multi-layer idempotency on broker-event/fill/learning ingestion are genuinely strong engineering. But the system also has real, previously-undiagnosed defects that fully explain the symptoms in the July 27 recovery report: a severe N+1-database-connection anti-pattern inside Kraken startup reconciliation, unbatched sequential per-symbol external API calls inside research jobs, a duplicate-scheduling bug between Render cron services and the always-on worker's internal scheduler, a governance and idempotency gap specifically on the **exit** order path (as opposed to the well-protected entry path), and a production topology bug that makes push notifications structurally unreachable — meaning the "always-on" system currently cannot proactively tell the Founder anything is wrong.

None of these are vague or hand-wavy findings. Each has an exact file and line number, and several were independently rediscovered by two different investigation passes approaching from different angles (the exit-order governance/idempotency gap, and the two-independent-canonical-trade-lifecycle-tables problem), which increases confidence that they are real rather than artifacts of one reviewer's misreading.

**This system should not be trusted with a meaningfully larger allocation of capital, and Kraken new-entry trading should remain paused, until the P0 items in `CRITICAL_REMEDIATION_PLAN.md` are fixed and re-verified in hosted production — not merely re-tested locally.** It should also not be declared "fixed" again based on a passing test suite or a clean deploy log, because this review found the existing test suite (Part 5, below) does not exercise Postgres, real brokers, concurrency, or restart-under-load — exactly the conditions under which the real defects found here manifest.

## What Genuinely Works

- **The connection/persistence abstraction is real and correctly enforced.** `database.py` is the sole chokepoint for all runtime database access; it fails closed (`RuntimeError`) if a hosted process ever resolves to a non-Postgres backend. No SQLite dependency exists in any code path reachable from `run-worker`, `run-job`, or `serve-api` — SQLite is genuinely confined to CLI dev tooling, `db_browser.py`, and tests. **`HOSTED PRODUCTION PROVEN`** that Postgres is configured as the backend for every Render service (`render.yaml`); **`NOT PROVEN`** by this review whether every table the application code expects actually exists in the live Supabase database (see the `LOGICAL_TRADES` gap below).
- **Job/child-process isolation for worker-loop-triggered jobs is real, not aspirational.** Each due job is run via `subprocess.Popen` (a genuine new OS process, not a `fork`), and a timed-out job is terminated with `SIGTERM` then `SIGKILL`, while the supervisor and subsequent jobs continue. This matches the recovery report's claim and was independently verified in code (`cli.py:544-583`).
- **Entry-order governance is unified and cannot be bypassed for the only two live-capable brokers.** Manual approval and autonomous execution both terminate in the same `InvestmentOrchestrator.evaluate_recommendation` call; Strategy maturity, Portfolio Manager, Risk Engine, and Production Risk Sentinel gates all sit on this one path (`orchestrator.py:117-432`).
- **Duplicate-order protection on entries is real and DB-enforced**, not just in-process: `acquire_order_intent_lock` uses a genuine `UNIQUE(broker, client_order_id)` constraint, acquired *before* the broker call, so a retried request is rejected before it can submit twice (`multi_broker.py:688-712`, `orchestrator.py:268-290`).
- **Kraken's exclusion of the Founder's pre-existing personal holdings from AI-managed accounting is careful, deliberate, and the single most well-engineered part of this codebase.** `KRAKEN_AI_ORDER_OWNERSHIP` requires an explicit `broker_order_id` match; unmatched events are explicitly classified `"unmanaged_excluded"` and never folded into AI-managed P&L or learning (`kraken_reconciliation.py:334-421`).
- **A filled entry is never mistaken for a closed trade.** Terminal state requires exit-filled quantity to match or exceed entry-filled quantity, computed from actual recorded fills — not from order acceptance status (`canonical_trades.py:447-503`).
- **Learning is fully automatic, doubly idempotent, and durable across restarts.** A terminal trade can only ever be enqueued once (DB `UNIQUE` key on the outbox), can only ever be processed once (a second, independent `UNIQUE` check on the run table), and a worker that dies mid-processing self-heals via a 10-minute claim-lease reclaim — with no manual trigger required anywhere in the chain.
- **The `/founder-evidence` read-model is honestly designed**, with a self-computed staleness flag that degrades the reported system state when the underlying snapshot goes stale, and a genuinely specific "why no trade" gate-reason system (five distinct states plus ranked reasons) rather than a generic "no action" message.
- **No secrets are committed to git**, `.env` files are properly gitignored, secret values are never logged (only presence booleans), and command/founder-only endpoints are gated server-side via constant-time token comparison — not merely hidden in the mobile UI.

## What Only Partially Works

- **Auto-execution evaluation ("`completed_no_action`") is a real, running evaluation — but it cannot currently be fed fresh research**, because the jobs that produce fresh research (`premarket-equity`, `overnight-crypto`) are timing out for identifiable, fixable reasons (see `PRODUCTION_TIMEOUT_ROOT_CAUSE_ANALYSIS.md`). The evaluation logic is not proven broken; it is proven starved.
- **Kraken startup reconciliation is architecturally sound (fill-based, ownership-gated, idempotent) but operationally too slow to complete**, due to a severe connection-per-row anti-pattern (opening a fresh database connection per helper call, per historical row, with no incremental cursor — re-scanning up to 1,000 rows from scratch on every single worker restart). This is a real, previously undiagnosed root cause, not a mystery.
- **Duplicate-order protection exists on the codebase's own terms — but only for entries.** The exact same protection (an intent lock acquired before the broker call) does not exist for exit orders (`monitor_managed_exits`, `force_managed_exit`), which is exactly the code path most exercised by the worker's own timeout-kill mechanism. This was independently found by two separate investigation passes.
- **Push notifications are fully implemented in code — and fully unreachable in the deployed topology.** `dispatch_pending_push_notifications` is real, correctly wired to Expo push, and registered on a 30-second interval — but that registration only executes inside the code branch that `AI_TRADER_DISABLE_API_BACKGROUND_WORKERS=true` (set identically on every Render service via the shared env anchor) disables. No other call site exists. The system durably records every incident and notification in the database; none of them currently reach the Founder's phone proactively.
- **Founder evidence staleness is computed correctly server-side but not consumed correctly client-side.** The mobile app's always-visible "Last refreshed" header reflects HTTP call success time, not the age of the underlying worker-owned snapshot — so it can read as fresh while the projection it's displaying is many minutes stale, precisely during the kind of evidence-snapshot-timeout incident this system is currently experiencing.

## Critical Architecture Findings

Ranked by blast radius, not by discovery order. Full technical detail and remediation for each is in `CRITICAL_REMEDIATION_PLAN.md`; root-cause detail for the timeout-specific items is in `PRODUCTION_TIMEOUT_ROOT_CAUSE_ANALYSIS.md`.

1. **Exit orders bypass all governance and lack duplicate-order protection.** `monitor_managed_exits` and `force_managed_exit` call `adapter.place_exit_order` directly, with no Portfolio Manager / Risk Engine / Sentinel check and no `acquire_order_intent_lock`-equivalent. Combined with the worker's own SIGTERM→SIGKILL timeout mechanism, a process killed between broker acceptance and DB confirmation leaves a position `status='open'` that the next cycle will re-evaluate and potentially re-submit. Kraken's `userref` is a client-side tag, not an exchange-side idempotency key, so this is not backstopped at the broker either. (`api.py:2695-2792`, `api.py:2794-2859` vs. the protected `orchestrator.py:268-290`.)

2. **An accepted Kraken order can become permanently untracked, unmanaged, and unlearned.** If the worker is killed in the narrow window after a broker accepts an entry order but before the local `link_broker_order`/`register_kraken_order_ownership` write completes, the recovery function that would normally backfill ownership explicitly excludes exactly this row (`result_order_id IS NOT NULL` filter), and the next broker-poll cycle actively re-classifies the AI's own order as `"unmanaged_excluded"` — as if a human had traded it manually. The position then never receives a managed exit, never enters the capital ledger or P&L, and never reaches the terminal state that triggers learning. This is a demonstrated gap in the code, independent of whether it has yet happened in production. (`orchestrator.py:254-354`, `kraken_reconciliation.py:272-278,356-367`.)

3. **Duplicate scheduling between Render cron services and the always-on worker's internal loop is real, not hypothetical, and the documented "cron jobs claim new idempotency keys, duplicates are skipped" safeguard does not actually protect against it.** The two schedulers compute structurally different `scheduled_for` strings for the same job names, so the `UNIQUE(idempotency_key)` constraint never collides between them. `overnight-crypto` is run by the worker loop every hour, 24/7, stacked on top of the cron's own every-2-hours schedule. Today's blast radius is doubled OpenAI/broker API cost and confusing duplicate evidence; the moment any `*_AUTO_TRADING` flag is enabled, it becomes a duplicate live-order-submission risk, because two independently-generated proposals for the same signal are not recognized as duplicates by any code path. (`render.yaml` vs. `cli.py:_due_worker_jobs`, `always_on.py:311-378`.)

4. **The reported job timeouts have specific, identified, fixable root causes — not "the timeout is too short."** `premarket-equity` makes three sequential, unbatched external calls (market data, news, OpenAI) *per symbol* for up to 30 symbols, each with independent timeouts and zero retries — a single slow response anywhere in the batch can exhaust the entire 180-second budget a fraction of the way through the universe, with no partial-completion checkpoint. `evidence-snapshot` makes up to 9 sequential broker HTTP calls (including one confirmed redundant duplicate call) with no batching. Kraken startup reconciliation opens on the order of 5–8 fresh Postgres connections *per historical row*, re-scanning up to 1,000 rows from scratch on every restart, with no incremental cursor. None of this requires new infrastructure to fix — it requires batching, connection reuse, and a cursor. Full detail in `PRODUCTION_TIMEOUT_ROOT_CAUSE_ANALYSIS.md`.

5. **Two independent, unreconciled "canonical trade lifecycle" subsystems exist, and a third exists for decision-stage logging.** `canonical_trades.py` (`LOGICAL_TRADES`, written at order-placement time) and `operational_truth.py` (`CANONICAL_TRADE_LIFECYCLE`, written at reconciliation time) both claim to be the authoritative trade-lifecycle representation, are populated from different entry points, and are never cross-checked against each other. The architecture documentation's claim of "one" canonical lifecycle does not match the code. A related finding: two independent P&L calculations exist for the same closed trade (`PERFORMANCE_ATTRIBUTION`'s single-price calculation vs. `LOGICAL_TRADES`' fill-weighted-average) that can diverge under partial fills, with no cross-check between them.

6. **`LOGICAL_TRADES`/`LOGICAL_TRADE_EVENTS`/`LOGICAL_TRADE_FILLS` — the tables that actually compute gross/net P&L and feed learning — have no code path that creates their schema on Postgres.** Every other schema module in the codebase unconditionally creates its tables on both backends; this module's schema initializer is skipped whenever `uses_postgres()` is true, and is absent from the API service's startup schema-initialization list. Whether these tables exist in the live Supabase database (created manually, out-of-band) is `NOT PROVEN` from this repository and should be checked directly against the database as the single highest-priority verification item arising from this review — if they don't exist, every live auto-execution attempt against Postgres would fail at the point of registering execution intent. (`canonical_trades.py:90-92`, `api.py:238-280` absent from list.)

7. **Push notifications are structurally dead in the deployed topology.** See "What Only Partially Works," above. This means every other failure-handling mechanism in the system — however well engineered — currently degrades from "the system will alert you" to "the system will tell you if you open the app and ask," which is a materially different and weaker guarantee than an "always-on autonomous" system implies.

## Hidden Gaps

These are gaps that would not be visible from documentation, dashboards, or a passing test suite — the specific "appears active without completing the lifecycle" pattern the Founder asked this review to expose:

- **A "fresh" Founder evidence snapshot can be wrong, not just stale.** The staleness check only detects a refresh job that has stopped running; it cannot detect a refresh job that keeps running successfully while its underlying aggregation query silently under-counts or mis-joins source rows. A correctness bug here would present as a perfectly healthy, perfectly fresh, perfectly wrong dashboard.
- **Portfolio/cash totals silently absorb a failed broker connection as `$0`** rather than flagging incompleteness, because the aggregate-sum guard checks "is the broker list non-empty" rather than "did every broker in the list actually report a real value." A failed broker still contributes a row (with an error field the Founder must separately find); its missing balance becomes an unflagged zero in the headline total.
- **The `/status` and `/developer-status` endpoints' `engine_health`/`sqlite` fields are structurally incapable of reporting real health in the deployed Postgres configuration** — they check for a local SQLite file's existence, which will never exist on Render. This field will report "Database not initialized" regardless of whether Postgres is perfectly healthy, on every deployed instance, unconditionally.
- **The Activity screen's evidence drill-down silently renders `"undefined #undefined"`** as the "Source" of every timeline event, and unconditionally claims "Raw Evidence: Not available" for every row — not because evidence is genuinely unavailable, but because the mobile app expects six fields the backend's timeline function has never populated. This looks like a data problem to the Founder; it is a contract mismatch.
- **The Learning and Market screens contain fully-built UI sections (strategy rankings, signal rankings, sector rotation, major themes) that are permanently empty by construction** — the client-side code that assembles their data hardcodes empty arrays/nulls, not because there's no data yet, but because the current `/founder-evidence` contract has no fields to fill them. These will never populate no matter how long the system runs, without a contract change.
- **A permanently-failed learning workflow does not raise an operational incident** — it is logged at a lower-visibility level that never flips the top-level "attention needed" status, so a trade that silently fails to be learned from three times over produces no alert on the primary health surface.
- **`bootstrap_kraken_order_ownership`, the function meant to recover from the order-orphaning window described in Critical Finding #2, structurally cannot recover the exact row it needs to** — its own filter excludes rows with no recorded broker order ID, which is precisely the signature of the orphaned row it exists to fix.

## Production Risks

Ranked by combination of likelihood and consequence, assuming the system continues to operate paper-only (Alpaca) / dry-run (Kraken) as currently configured, and separately noting what changes the moment live trading is enabled:

| Risk | Current exposure | Exposure once live Kraken trading is enabled |
|---|---|---|
| Duplicate exit order submitted after a timeout-kill | Real, but consequence-free while `KRAKEN_SUBMIT_REAL_ORDERS=false` (Kraken returns a dry-run validation, not a real fill) | **Real financial risk** — a duplicate live sell/buy could execute; only backstop is Kraken's own balance check |
| Orphaned Kraken order (permanently unmanaged position) | Real in code, dry-run consequence-free today | **Real financial risk** — an unmanaged live position with no stop-loss/take-profit monitoring |
| Duplicate scheduling → duplicate proposals | Real today (doubled API cost, confusing evidence) | **Real financial risk** — two independently-generated proposals for the same signal are not deduplicated by proposal ID |
| Token exposure incident | Low — Alpaca is structurally paper-only, Kraken is double-gated to dry-run; holder could read data, pause/resume the engine, and burn OpenAI spend, but cannot move real capital today | Becomes a live-trading-command credential the moment Kraken is enabled — must be rotated first |
| Founder not proactively alerted to any incident | Real today, regardless of live/paper status | Unchanged — this is a visibility gap independent of trading mode |
| Two Postgres-canonical-trade-lifecycle systems disagreeing | Real today, affects evidence/learning correctness | Unchanged in kind, higher stakes given real money |
