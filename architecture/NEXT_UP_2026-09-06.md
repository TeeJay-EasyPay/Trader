Written at the end of the egress session so nothing is carried in anyone's head.

## 1. Record why a trade was SOLD

Every closed trade currently says "Exit trigger was not recorded for this trade."
The system knows why it bought and what it made; it does not know why it sold
(stop loss, target, AI decision, fee hurdle, manual). Half the lesson is missing
from the AI's own record.

Founder's framing, and the through-line of the whole session: give the AI more to
judge with, never another rule telling it what to do.

## 2. Fees versus trade size

The XRP position closed 2026-09-05 23:38 UTC called the direction correctly and
still lost money:

    bought  GBP 25.04    sold  GBP 25.11    price  +0.07    fees  -0.40    NET  -0.33

Kraken costs roughly 1.6% round trip on a stake that size, so price has to beat
that before anything is kept. NOT to be fixed with a hardcoded minimum size --
same objection as every other gate. The AI already records the NET result
(PERFORMANCE_ATTRIBUTION.profit_loss is net_pnl, verified), so it can learn this;
the question is whether it is given the fee maths clearly enough to reason about
BEFORE entering.

## 3. App Technicals screen (Founder request)

A health view of the whole ecosystem, so we can see whether the app and the AI
are working optimally rather than inferring it.

Wanted: egress, database size, trades, times Kraken was polled, times the database
was written to, other technicals. Hourly refresh. A dated log so any past day can
be selected.

READABLE FROM POSTGRES DIRECTLY (easy):
  - database size, and size per table
  - database writes, reads, and per-query counts (pg_stat_statements)
  - Kraken poll counts, trades opened/closed, job runs, worker restarts
  - an EGRESS ESTIMATE, from rows x measured column widths -- the model built this
    session reconciled to 0.96 GB/day against a measured 1.28

NEEDS A CREDENTIAL WE DO NOT HAVE:
  - the REAL Supabase egress figure. Only AUDIT_DATABASE_URL exists; there is no
    Supabase management API token. The Founder can create one, or the screen shows
    the estimate and links out to the dashboard for the authoritative number.

DESIGN RULE, non-negotiable: a screen that watches the bill must not add to it.
Counters get computed once an hour by the worker into one small row, and the app
reads that row. It must never run pg_stat_statements queries per view -- that is
precisely the mistake that put the /founder-evidence blob on a 2-minute loop.
